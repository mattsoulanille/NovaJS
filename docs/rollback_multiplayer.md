# Rollback Multiplayer Plan

This document is the plan for adding rollback netcode (deterministic lockstep with rewind/resimulate) to NovaJS. It replaces the earlier notes version of this file and builds on the completed work in [docs/engine_in_webworker.md](./engine_in_webworker.md).

## The Model

- Every peer in a star system runs the full simulation for that system.
- The only thing exchanged over the network is per-tick player input, plus occasional snapshots for joins and desync recovery.
- Each peer predicts remote inputs (repeat-last-input), and when real inputs arrive for a past tick, it rolls back to a stored snapshot, applies the true inputs, and resimulates to the present.
- The server stops being a simulation authority within a system and becomes an input relay, tick clock, and snapshot archive for late joiners. Because the sim is deterministic, the server *can* still run any room's simulation like any other peer (for NPC authority, validation, or persistence) — but steady-state NPC behavior is computed identically by every peer and needs no owner. (Today all NPCs are simulated by clients.)
- The existing room-per-system infrastructure (`multi_room_communicator.ts`) is reused as-is: rollback state is scoped to one star system's world, which keeps entity counts and snapshot sizes bounded.
- **All peers run the same build of NovaJS.** This is an assumption the whole model rests on — nothing reconciles two builds, so a peer running different code desyncs on contact — and it is *enforced*, not hoped for, by the build-version handshake described in Phase 3 item 7. A client on a stale build is refused the room and reloads itself.

## Why the plan has this shape

The original three steps (worker split, determinism, state history) are the right skeleton, but two of them hide most of the work, and the ordering within them matters:

1. **Step 1 (worker split) is structurally done** on the `worker` branch (lingering issues in Phase 0 below) and its shape is right for rollback: input already crosses the bridge as normalized `ControlEvent`s/commands, the sim world is free of PIXI/browser state, and display consumes snapshots. Nothing about the current bridge design blocks rollback.
2. **Step 2 (determinism) is the long pole**, and it is much more than fixed timestep + seeded RNG. The audit below found six categories of nondeterminism, of which async data loading inside the simulation is the most invasive to fix.
3. **Step 3 (state history) should be built and validated entirely locally** — rollback correctness can be tested with zero networking by feeding the sim its own inputs with artificial delay. The network protocol is the *last* thing to build, not part of step 3.
4. A step the original plan was missing: **a determinism verification harness must come first**, not last. Without per-tick state hashing and record/replay tests, desyncs are undebuggable. Every subsequent change gets validated against this harness.

## Determinism audit findings

What must change in the current code, by category:

| Category | Sites | Notes |
|---|---|---|
| Variable timestep | `time_plugin.ts:20-27` | `delta_ms` from wall clock each frame; foundation fix |
| Wall-clock time in gameplay | `stat.ts:160`, `npc_plugin.ts:32` (via `time.time`), `projectile_plugin.ts:196` (fire time) | must become tick-derived logical time |
| `Math.random()` in sim | `fire_weapon_plugin.ts:101,130`, `make_ship.ts:17-19`, `ship_plugin.ts:166-168`, `npc_plugin.ts:45` | ~6 sites; replace with a seeded PRNG resource. Display-world uses of `Math.random` (explosions, beams, animation jitter) are fine and stay. |
| Random entity UUIDs | `projectile_plugin.ts:177,378`, `bay_plugin.ts:118`, `beam_plugin.ts:109` | `v4()` per spawn; replace with deterministic IDs (e.g. `${spawnTick}:${counter}`); counter becomes snapshotted state |
| Async in the sim step path | `ProvideAsync`/`AsyncSystem` uses: `ship_plugin.ts`, `outfit_plugin.ts`, `planet_plugin.ts`, `projectile_plugin.ts:245`, `collisions_plugin.ts:140` (hulls), `fire_weapon_plugin.ts:361` (weapon data), `make_system.ts:22` | **The most invasive item.** Components appear on entities at a tick that depends on cache warmth. All static game data must be resolved *before* an entity enters the sim world (preload at system creation / spawn time), making these providers synchronous. |
| Cross-engine float math | trig throughout movement/weapons | IEEE 754 `+ - * / sqrt` are deterministic everywhere; `Math.sin/cos/atan2/pow` are **not guaranteed identical across JS engines**. Decision: assume latest Chrome for all clients, and periodically broadcast full position/velocity/rotation for ships as a drift backstop. Projectiles are short-lived enough not to matter. |

Things that are already in good shape:

- System execution order is topologically sorted and stable given stable plugin registration order (`world.ts:266`).
- Entity iteration is Map insertion order — deterministic, **but snapshot restore must rebuild the entity map in the recorded order**, or post-rollback iteration diverges from the original timeline.
- The event queue is synchronous FIFO within a step.
- Input already flows as per-tick `ControlStateEvent`s and bridge commands rather than direct mutation.
- `randomAdmin()` in `multiplayer_plugin.ts:173` is network-layer, not sim state; it doesn't need fixing for determinism.

## Phases

### Phase 0: Land the worker branch

Do not abandon `worker` (branched off `turborepo`). The sim/display split's shape is exactly what rollback needs. Finish and commit the in-flight work; rollback work happens on a new branch on top of it.

Known lingering issues to resolve or explicitly defer:

1. ~~Desync when a ship dies~~ **Fixed.** Root cause: every peer (including the server's replica worlds, which run their own weapons fire with unseeded RNG) decided deaths independently and deleted entities locally, racing the owner's deltas — dead ships could resurrect via state requests or persist as zombies on peers that missed the removal. Entity removal now has a single authority (the owner's sim; death VFX still run everywhere), and state-request responses report unknown entities as removed. Additionally, `MovementState` deltas were only sent on input changes, so the respawn teleport after a player death never reached other players — discontinuous moves now bump a `teleportCount` field that forces a full movement state send (`teleport()` in the movement plugin; use it for any future respawn/blink mechanics instead of writing `position` directly). This is a patch over the divergent-simulation model, not a cure — the cure is rollback itself. Still open from that investigation: one unreproduced total sim freeze (worker wedged silently, no errors — observed once, before these fixes, with a point-defense-equipped player ship), rapid spawn/despawn cycling of unnamed bay fighters, and a stray `window is not defined` rejection from the worker bundle.
2. ~~Per-frame sync performance~~ **Investigated and largely fixed.** Benchmarking (`snapshot_benchmark.ts`) plus a Chrome trace showed the worker was ~82% idle and the cost was on the main thread: full-frame apply re-setting every component of every entity each frame, which fanned out through the ECS query-cache invalidation, plus Immer overhead in the multiplayer DeltaMaker. The bridge now sends delta frames (host string-compares each component's encoded form against the last frame — no Immer), cutting frame size ~5x and main-thread clone+decode ~3x. Remaining known main-thread costs, deferred: PIXI `removeChild`/`removeItems` churn from transient entities and particle emitter update/upload (display-layer, unrelated to sync), and ECS query-cache invalidation cost in general (matters again for rollback resimulation; see Phase 1).

### Phase 1: Determinism foundation (single-player, no networking)

1. ~~**Determinism harness first.**~~ **Done.** `hashWorld`/`diffWorldHashes` (nova_ecs `world_hash.ts`) hash all serializer-registered entity state in canonical order; `determinism_harness.ts` steps two identical worlds in lockstep and reports the first divergent tick and entities. `determinism_test.ts` is the CI gate: a quiet world is bit-identical over 240 steps. `determinism_check.js [npcs] [steps]` is the diagnostic — with NPCs it correctly reports divergence (Math.random + v4 uuids, items 4–5). Pause/single-step ship as `window.novaSim.pause()/.resume()/.step(n)`.
2. ~~**Fixed timestep.**~~ **Done, 60 Hz.** `FixedTimestepResource` + `useFixedTimestep(world, delta_ms)` in the time plugin; `makeSystem` puts every simulation world on fixed, 0-based time. The client pump and the server stepper own accumulators (bounded catch-up; the server additionally bounds steps per timer callback so stepping can't starve its HTTP serving). Two discoveries: the display world had been running on *simulation* time copied in every frame — it now has its own wall-clock `TimePlugin` (`addSystem` requires `TimeResource` to exist); and `Optional()` does not support absent resources (`getArg` throws), so optional resources are read via `GetWorld`.
3. ~~**Logical time.**~~ **Done by construction:** with the fixed timestep, `time.time` is tick-derived logical time, so its consumers (projectile lifespan via `CreateTime`, NPC retarget timers) are deterministic. `stat.ts` delta throttling still uses the wall clock deliberately — it is network-layer pacing, not simulation state.
4. ~~**Seeded RNG resource.**~~ **Done.** `Random` (sfc32) + `RandomResource` in nova_ecs, seeded per system from `fnv1a(systemId)` in `makeSystem`; state is get/settable for snapshots. Converted: weapon inaccuracy, submunition cones, beam inaccuracy, NPC target selection, ship spawn position provider. `make_ship.ts` keeps `Math.random` deliberately (creation-time state for player-spawned ships, synced as full state, never re-derived by the sim).
5. ~~**Deterministic entity IDs.**~~ **Done.** `IdFactory` resource (`kind:counter` ids) replaces `v4()` for projectiles, blasts, beams, and bay ships (bay ids are prefixed with the multiplayer owner since they sync across peers). The counter is simulation state: include it in rollback snapshots along with the RNG state.

**Milestone:** the determinism gate now passes *with NPC combat* — 8 NPCs fighting for 1200 steps produce bit-identical state hashes across two runs (`determinism_check.js 8 1200`), and a 4-NPC/240-step variant runs in CI. Caveat: both runs share warm game-data caches; item 6 still owns the cold-cache/cross-machine async-loading risk.
6. ~~**Synchronous data access in the sim.**~~ **Done — "stage, load, then insert."** Rather than preloading the full game files (too expensive), entities are staged: before insertion, `entity_data_loader.ts` loads the *transitive closure* of game data the entity and anything it can spawn will need synchronously (ship → outfits → weapons → submunition chains → hurtbox sprite sheets → bay fighter classes, recursively), and primes the lazily-built `WeaponEntries`. The insertion tick is an input, so it may vary; what never varies is data resolving mid-step. All sim `ProvideAsync`s became `ProvideFromCache` (synchronous, reading warmed `getCached`; may return undefined = retry next step), `makeSystem` loads planets before the world ever steps, and the bridge's `addEntity`/`spawnNpc` stage before inserting. Result: **worlds are deterministic from tick 0 with zero warmup** — the CI gates now assert this. Deferred to Phase 3: entities arriving via multiplayer state bypass staging and use the retry path (self-healing but with a varying attach tick); the input-exchange protocol should stage them too, buffering deltas for staged entities and applying them on insertion.
7. **Decision checkpoint: passed.** Same-machine replay is bit-identical from tick 0 (quiet and combat worlds); cross-browser trig is deferred per the Chrome-only decision. Phase 2 (snapshot/restore + local rollback) is unblocked.

### Phase 2: Snapshot, restore, and local rollback

0. ~~**Entity deriver registry.**~~ **Done.** Derived components (ship data, outfits, physics, weapons state, planet data) are now attached by *derivers* — `{provided, requires, derive}` entries that plugins register next to their systems (`entity_factory.ts`), run to a fixpoint by `completeEntity` at staged insertion. This keeps mod ergonomics (register a deriver, no central factory to edit) while making derivation synchronous and callable anywhere — which snapshot restore requires: a restored entity must be complete *before* resimulation begins, not one tick later. The `Provide`/`ProvideFromCache` systems remain as the fallback layer for un-staged arrivals; they get deleted when Phase 3 stages all ingress. Remaining sync-only providers (animation, hulls, shields, targets…) migrate to derivers as part of deciding the snapshot representation below (snapshot-and-restore them vs. re-derive on restore).
1. ~~**Full-world snapshot.**~~ **Done.** `snapshotWorld`/`restoreWorld` (nova_ecs `snapshot_plugin.ts`) with a per-component policy registry configured in nova (`snapshot_policies.ts`): **codec** (io-ts roundtrip, the default for registered components; the encoded form is structurally cloned because io-ts optimizes all-identity codecs to return the *live object* — the sneakiest bug of the effort), **share** (immutable static data like ShipData, and per-step-recomputed structures like hulls — the structural-sharing win), **clone** (mutable unregistered state: weapon reload timers, sub counts, collision sets), **skip** (multiplayer machinery; re-derived state like ShipPhysics, reattached synchronously via the deriver registry at restore). Resources: time, RNG state, id counter, control state. Entities restore in insertion order; restore discards the Add/Delete events its own surgery queues (`World.clearEventQueue`), since snapshots are taken between steps. The unhandled-component list is asserted empty in CI so new state can't silently bypass snapshots. Also fixed en route: projectile entity pooling (`FactoryQueue`) removed — the pool was unsnapshotted state (resim dequeued different objects, leaking `targetSpeed`/`BlastIgnore` across timelines); projectiles are built fresh per shot, and display-side sprite pooling already covers the perf motivation. **Acceptance (CI): restore is hash-exact, 180 steps of NPC combat resimulate bit-identically after restore, and repeated restores from one snapshot yield identical runs.** Measured on a 99-entity combat world: snapshot 0.76ms mean (snapshot-every-tick at 60 Hz is affordable), restore 4.2ms, step ~1.1ms — a 10-tick rollback ≈ one frame budget.
2. ~~**Ring buffer.**~~ 3. ~~**Rollback driver.**~~ 4. ~~**Local validation.**~~ **All done** — `RollbackSimulation` (nova_ecs `rollback_plugin.ts`): a snapshot ring buffer (default 64 ticks) plus a tick-keyed input history, with `setInputs(tick, inputs)` / `step()` / `rollbackTo(tick)`. The driver is prediction- and network-agnostic: whoever owns the network amends past inputs and requests the rollback. Both validation harnesses pass in CI with real control inputs steering the ship through combat: the *rollback fuzz test* (random inputs, random rollback depths → bit-identical to the straight-line run) and the *delayed-echo test* (inputs arrive 8 ticks late against a no-new-input prediction, corrected by rollback → converges exactly to the undelayed run). This is the netcode loop, minus the sockets.
5. ~~**Performance budget.**~~ **Measured** (99-entity combat world): snapshot 0.76 ms, restore 4.2 ms, step 1.1 ms — snapshot-every-tick at 60 Hz is affordable and a 10-tick rollback fits in roughly one frame.

**Phase 2 is complete.** ~~Flagged for Phase 3: platform-gated sim systems.~~ **Fixed**: `ShipController` and `WeaponPlugin` built different system sets per platform (an uncaught bug — clients controlled all NPCs, so the server never noticed). All simulation systems now build on every platform; only keyboard capture and key-mapping loading stay browser-side. A CI gate asserts a node world and a worker world simulate identically through combat with inputs. This also killed the recurring `window is not defined` worker rejection (`SetControlledShip` touched `window` unguarded). Node test harnesses use the `'worker'` platform (with a disk-backed `getSettings`) to match the real client sim. Parked: on player death, restore the player's entity state from a snapshot taken at launch/jump-in (per-entity restore is a natural extension of the snapshot machinery) instead of teleporting to the origin.

### Phase 3: Input-exchange network protocol

1. ~~**Tick-stamped input message.**~~ **Done (local).** `SimulationInput` (`simulation_input.ts`): control events, entity insertion/removal, jump route — structured-cloneable records applied at the start of their tick. The bridge host no longer mutates the world: it stages (loads an entity's data closure), then *schedules* an input, and `RollbackSimulation` records and applies it — the identical path resimulation replays. NPC spawns are staged host-side and become insertion inputs (which required registering the NPC AI components with the serializer, multiplayer-excluded, so they survive the encode roundtrip). Single-player now runs the netcode loop with one peer, and `window.novaSim.rewind(ticks)` live-rewinds the game — verified in the browser. Still missing for the wire: `peerId` scoping (jump route targets the local `PlayerShipSelector` for now) and land/depart as inputs. Note: incoming *multiplayer* messages still mutate state outside the input model; steps 2–3 replace that pipeline.
2. ~~**Server as relay + clock + archive.**~~ **Done.** `RollbackRelay` (one per room, beside the legacy world): relays each peer's tick-stamped input records to the other peers — stamping the sender's identity and clamping ticks so nobody speaks for others or injects inputs into the past — advances the canonical tick at the fixed rate, broadcasts it via periodic `tickSync`, retains the input log, and serves it on `inputLogRequest` (the late-join archive). Protocol messages share the room channel with legacy multiplayer inside a `rollback` envelope (each side ignores the other's shapes). The bridge host publishes its input records as it steps and buffers relayed remote records + the server tick for step 3. Verified live: the server clock reaches the client at 60 ticks/s, and the archive returns the room's tick-stamped, peer-attributed input history. With the cutover, the server stopped being a simulation *authority* — each active room is a `RollbackRelay`. **The periodic snapshot archive is done**, and it brought a new capability with it: *wire snapshots* (`wireSnapshotWorld` in the snapshot plugin), a JSON-safe complete world state, unlike rollback's in-memory snapshots which hold live references. Serializer-registered components cross through their codecs; the rest get explicit wire codecs in `snapshot_policies.ts` (Maps, Sets, DefaultMaps, control state) or are marked wire-derived; hulls cross as resting geometry (`encodeHull` — one codec instead of re-deriving along their four different creation paths); non-finite numbers and `undefined` are sentinel-wrapped (JSON silently corrupts both — inertialess ships have `Infinity` max velocity, markers encode to `undefined`). Completeness is CI-gated the same way as snapshot policies: an `unhandledWire` set asserted empty, plus the real gate — `wire_snapshot_test.ts` captures a mid-combat world (missiles, turret bolts, held controls, damaged carriers) as JSON, restores it into a fresh world, and requires 240 ticks of lockstep bit-identity. Each active room runs a `RoomArchive`: a trailing sim that steps only to the relay's clock and therefore *never rolls back* (the relay clamps every arriving record to a future tick, so inputs at or before its clock are final), wire-snapshotting every 30s and trimming the relay's log behind the baseline — memory and join cost are both bounded. `catchUp` now carries the baseline, and joiners (and desync resyncs, which share the path) restore it and replay only the tail: a live resync in a 60-second-old room took ~27ms against the archived baseline. Also fixed while wiring staging: replayed insertion records and baseline entities are staged (`loadInputRecordsGameData`/`loadWireSnapshotGameData`) before applying — previously a truly cold-cache joiner would have derived entities against unloaded game data. Known residuals: the archive catches up in ~60-tick batches on the node event loop (~60ms/s per active room; fine at current scale), and `restoreComponents` now clones before decoding (identity codecs hand the snapshot's own object to the entity — a restored-twice snapshot would have seen the first timeline's mutations, a latent rollback hazard).
3. **Prediction and delay.** *Per-peer input application done.* Control state moved from a global resource to a per-ship `ShipControlStateComponent`, with a synced `ControlledBy(peerId)` marker mapping peers to ships; all edge-triggered consumers (landing, targeting, weapon selection, jumping) converted from the global `ControlStateEvent` to a per-ship targeted `ShipControlEvent`, so any number of ships are steered identically by their peers' records. The rollback driver's inputs are now full `InputRecord`s, applied in peerId-sorted order for cross-peer determinism, and the bridge host folds relayed remote records into the timeline — rolling back to the earliest late correction (records older than the buffer clamp forward rather than drop; desync detection owns that case). CI includes the full two-peer steady state with zero sockets: two worlds exchanging both peers' input schedules with a 6-tick delay and rollback corrections converge to bit-identical hashes. **The cutover to pure input-driven rooms is done**: the worker no longer adds the delta-sync multiplayer plugin, and rooms exchange nothing but input records. Joining is *reconstruction*: deterministic genesis (`makeSystem`) plus the relay's input log, replayed via `fastForward` (snapshotting only the final buffer window). Peer disconnects are server-authored `removePeer` input records, so departures live in the log too. The death/bay ownership gates are gone — in a deterministic room every peer computes deaths and launches identically, and no removal message exists at all. Peer-local UI markers (`PlayerShipSelector`, now derived from `ControlledBy` + local peer id) are excluded from cross-peer hashes via `PEER_LOCAL_COMPONENTS`; two `PlayerShipSelector`-gated providers (jump route, active secondary) were re-gated on `ControlledBy` since they are shared sim state. One topology lesson baked into the code: peers publish records to the *server only* — broadcasting them made peers receive records twice (direct + relayed), double-firing edge events. CI: two full bridge hosts over a real relay converge exchanging only input records, and a late joiner reconstructs the running world from the log. **Tick pacing is done, as a smooth clock slew** (never skipped/doubled ticks): the bridge extrapolates the server's tick between `tickSync`s, targets it plus a small send-ahead lead (4 ticks — so records reach the relay before its clock passes them; a record behind the relay clock gets retimed for the room but not its sender, a divergence), and reports a rate factor (±5% max, 1%/tick of drift, lightly smoothed against sync jitter) in each frame. The pump multiplies real elapsed time by the rate, so correction is time running imperceptibly fast or slow. Only gross divergence (>30 ticks — a hidden tab, a long stall) snaps, stepping the backlog at up to 60 ticks/frame. Verified live: steady state holds within ±1 tick of target at rate ≈1±0.01, and a 2-second stall recovers within ~2 frames. `window.novaSim.pacing` shows the live rate/drift. Remaining: input delay tuning.
4. ~~**Desync detection and recovery.**~~ **Done.** Every 60 ticks each peer hashes its world (`hashWorld` with the `PEER_LOCAL_COMPONENTS` exclusion) and publishes the checkpoint to the relay once it is 30 ticks old — past any realistic rollback depth, so the hashed state is settled. The rollback driver's new `onStep` hook fires on resimulated ticks too, so a rollback that crosses a still-pending checkpoint recomputes its hash from the corrected timeline (`rewind` instead discards pending checkpoints from the abandoned future). The relay compares a tick's reports once every peer has weighed in (a periodic sweep force-compares sets that a leaver/joiner left incomplete) and broadcasts a `desync` with all hashes on mismatch. Recovery is *not* the old full-state machinery (gone since the cutover): the canonical hash is chosen by majority vote with ties toward the lowest peerId — every peer computes the same answer, so exactly the minority resyncs — and a diverged peer rebuilds like a late joiner, restoring a pinned genesis snapshot and replaying the relay's log (`resync()`, auto-triggered with a 10s cooldown; `window.novaSim.resync()` for manual testing). Found along the way: records relayed while a `joinRequest` was in flight are also in the catch-up log, so they were applied twice — `joinRoom` now drops the buffered remote records when the reply arrives. Known residual: a rollback deeper than the 30-tick settle margin can invalidate an already-published hash and cause a false positive; recovery is disruptive but safe, and the margin tunes together with input delay. CI: relay comparison unit tests, plus an end-to-end test where a peer corrupted mid-run is detected at the next checkpoint and converges back to the canonical hash after resync. **Hardened by the two-browser live test**, which caught three real bugs the shared-fixture mock tests masked: (1) live-relayed `addEntity` records were applied with *cold caches* on every peer but the sender — the remote copy derived against unloaded game data and silently diverged forever; records now stage their game data before integrating (a record that stages slowly just integrates as a deeper rollback, and a generation counter drops in-flight staged records superseded by a catch-up log); (2) with exactly two peers, the lowest-peerId tie-break crowned the *diverged* client canonical, making divergence permanent — the room's archive sim (the log's true simulation) now joins every hash comparison as a standing witness under the server's identity, which both breaks two-peer ties and convicts a lone diverged peer whose roommates are throttled background tabs, and `canonicalDesyncHash` prefers the server's group on remaining ties; (3) insertion records carried the sender's `PlayerShipSelector`, so other peers briefly treated the new ship as *their* player ship — one player landing docked every client's UI, and the spaceport ship-purchase flow then had two clients fighting over one uuid; peer-local components are now stripped from published records (each peer derives its own from `ControlledBy`). Live end state: a full session (two browsers, join/leave via Firefox+Chrome, flying in formation, landing, buying a Leviathan, a forced `novaSim.rewind` divergence) produced exactly one desync line per real divergence, each convicted by the archive witness and healed by a single resync. Known residual: transient checkpoint mismatches in a join window (hashes published before slow-staged insertions finish crossing) recover via resync but could be tuned away with a larger settle margin — input-delay-tuning territory. **A second live round found three more:** (4) local inputs were stamped at the local tick even while catching up (join, resync, stalls), so they arrived behind the relay clock and got retimed for everyone but the sender — a divergence loop that lasted as long as the player kept typing; inputs are now stamped at the extrapolated server clock when it leads. (5) `joinRoom` fast-forwarded to the catch-up reply's tick, stale by seconds of cold-cache asset staging, so play began far behind and the pump snapped through the gap at a visible ~60× fast-forward ("my ship is extremely fast"); joins now fast-forward to the extrapolated clock. (6) Ships bought at the shipyard carried no `ControlledBy`/`MultiplayerData` — uncontrollable after departure, and `removePeer` left them behind as invincible orphans on disconnect. **Resolved after two more live rounds**: player deaths desynced because `PlayerDeathSystem` (respawn) was gated on peer-local `PlayerShipSelector` — only the owner's world revived the ship; now gated on synced `ControlledBy` (third instance of the "whose event/state is this?" class, after landing and jumping; also: untargeted `ChangeSecondaryEvent` redrew every player's status bar). The recurring "archive diverged from all peers" episodes were mostly **report-timing false positives**: a rollback correction landing deeper than the 30-tick settle margin corrects every peer's world, but their already-sent checkpoint hashes describe the abandoned timeline; the archive (which never predicts) reports the true one, and everything re-agrees a checkpoint later without any resync — the tell that worlds never actually diverged. The relay now convicts only after 3 *consecutive* mismatched checkpoints (`desyncThreshold`); blips never repeat, real divergence persists and is caught ~3s in. CI's strongest gate: two worker peers + the node archive through 900 ticks of Carrier + Raven (beams, PD) combat killing the player's shuttle — bit-identical through death and respawn. **RESOLVED — the archive-vs-browsers class was cross-engine trig** (found via a dev-branch report of persistent desyncs when a weapon hits a ship): node 24 and current Chrome disagree at the ulp level on sin, cos, tan, atan, atan2, asin, acos, exp, and log (bit-hash measured; sqrt/pow/hypot/cbrt agree), and every hit runs atan2/sin/cos (knockback, guidance, SAT hull rotations). `nova_ecs/deterministic_math.ts` now provides fdlibm-style implementations built from exact IEEE operations only — verified bit-identical node-vs-Chrome by hashing 40k outputs — and `makeSystem` installs them onto the global Math in every simulating context (which also covers SAT.js internals); display contexts keep native Math. Live: minutes of Chrome-vs-archive combat with point-blank hits, zero desyncs. Previously: Previously open: one observed episode where *both* peers agreed and the **archive** was the odd one out persistently (its baselines are poisoned from that point; the relay logs `Archive diverged from all peers` loudly — only fired now after a sustained streak). The land/purchase/relaunch sequence is covered by a passing regression test, so the suspected trigger is the (now-fixed) retiming storm; needs a watch on the next live session, and eventually automatic archive rebuild. **(8) One player's hyperjump dragged every client in the room with them**: the display followed *any* `FinishJumpEvent` to the new system (a pre-rollback assumption — only the local player's jump used to exist), so the origin room's remaining clients tore down their worlds, "jumped" carrying a copy of the jumper's ship, collided over its uuid in the destination room, and black-screened. Now filtered to the local player via the event entity's `PlayerShipSelector` (the sim removes the jumping ship the same frame, so the display entity cannot be consulted) — the same class and fix as the phantom-docking bug; **any display-layer subscriber to sim events must ask "whose event is this?"**. (7) The big one, found via system jumps (`No rollback relay responded; starting at tick 0`): the main thread awaited the worker's init — which awaits `joinRoom` — *before* subscribing room messages for forwarding to the worker, so every join's catch-up reply was dropped and the world silently started at tick 0 in a room whose timeline could be thousands of ticks old. Initial joins were papered over by the first desync's resync (the recurring "join-window transient" was actually this); jumps made it visible because the rejoined room has real history. The subscription now precedes init and the worker buffers pre-init room traffic. Verified live: fresh join and history-rejoin both report `joined: true` with **zero** desyncs — the first sessions with no join transient at all. `window.novaSim.status()` now surfaces the worker's tick, desync count, join result, and recent worker console lines. **(9) Desyncs seconds after every hyperjump**: the arriving ship's insertion record was stamped before the fresh room's first periodic tickSync arrived (jump insertions are fast — warm assets — unlike cold first loads), so it used the local tick, trailed the relay clock, and got retimed for everyone but the sender: the jumper's own ship diverged until the first resync rebuilt it from the retimed log. Fixed by seeding the clock estimate from the catch-up reply (it carries the relay's tick). Diagnosed with the new `node_client.mjs` rig — a real node client joining the live room and dumping per-entity hashes for a same-tick diff against a parked Chrome client — which first proved 166k ticks of cross-engine asteroid simulation bit-identical, then isolated the divergence to exactly one entity: the jumper's ship. Four consecutive live jumps now run desync-free.
5. **NPC and world authority.** NPCs, projectiles, and all sim-derived entities are simulated identically by every peer and have no owner. `MultiplayerData` ownership shrinks to mapping peers to their input streams (which ship each peer controls). Within a rollback room, this *replaces* the delta-based sync of `multiplayer_plugin.ts`.
6. **Join and system transition.** A joining peer receives the latest server snapshot + the input log since that snapshot, simulates forward to the live tick, then participates normally. Hyperspace jumps are a leave/join across rooms. Before any of this, the peer must pass the build-version handshake (item 7) — a socket that fails it never becomes a room member, so no join is ever attempted from a mismatched build.
7. ~~**Build-version handshake.**~~ **Done.** The model assumes every peer runs the same build; this is what makes that true. A build stamp is generated at build time by `scripts/generate_build_version.mjs` into `src/common/generated_build_version.ts` — the *commit sha* for a clean tree, `<sha>-dirty-<epochMs>` for a dev tree — and compiled into **both** outputs from the same text, so the server process and the bundle it serves cannot drift (the server is `tsc`-compiled, the client is esbuild-bundled; an esbuild `define` would only have reached one of them). Two enforcement points, both driven by the pure logic in `src/common/version_handshake.ts`: (a) the client announces its stamp on the websocket connect URL (`ws://host/?v=<stamp>`), and `SocketChannelServer` compares it **before** registering the client or firing `clientConnect` — a mismatch, or a bundle old enough to announce nothing at all, is closed with application code `4001` and never becomes a channel client, so it cannot join any room; (b) the browser separately preflights `GET /version` on load. A mismatch on either route shows "Game updated — reloading…" and reloads once. No cache-busting parameter is needed or used: `setup_routes.ts` already serves index.html and every bundle with `Cache-Control: no-cache`, so a plain `location.reload()` revalidates, and a query parameter would collide with the `?enter`/`?ship`/`?system`/`?char` startup parameters. The reload is **loop-guarded** by a `sessionStorage` marker set *before* the reload: a client that still mismatches after one automatic reload stops and shows a persistent hard-refresh message instead of reloading forever, which is also what keeps a hand-restarted dev server serving a stale bundle from spinning the page. A successful match clears the marker, re-arming the one-reload budget for the next deploy. Relationship to the older `PROTOCOL_VERSION` machinery: that number and the relay's `peerProtocols`/`mismatchStreaks` are **forensic** — they run after a peer has already joined and can only report a skew once it has had the chance to desync. This handshake is **preventive** and strictly earlier. `PROTOCOL_VERSION` is kept (it labels incident records, and is the last line of defense for any path that bypasses the socket gate), but it is no longer what stops builds from mixing. Trade-off accepted: any rebuild of a dirty tree changes the stamp and force-reloads connected clients, even if the bundle is byte-identical.

### Phase 4: Hardening and polish

Only after 3 works end-to-end: input compression/batching, tuning input delay vs. rollback depth, spectators, and replay files (which fall out of the input log for free).

**Done: the desync black-box recorder** — the long-tail net for divergences that survive everything above. On conviction, the diverged peer uploads its state history *before* resyncing discards the evidence: full wire snapshots at its last 8 checkpoint ticks (pinned from the rollback ring's structural snapshots — free until a desync actually happens; `wireSnapshotOfSnapshot` encodes them to wire form without touching the live world) plus a rollback event log (joins, resyncs, rollbacks with depths, late records — the *how it got there* that state alone can't show). The server's `DesyncRecorder` writes each incident to `desyncs/<timestamp>_<room>_tick<N>/`: `desync.json` (the verdict — all hashes, canonical, convicted, archive-outvoted), `baselines.json` + `log.json` (the server side is reproducible from these alone; the archive now retains its *previous* baseline too, since the newest can postdate the incident window, and trims the log only behind it), and `client_<peer>.json` when the upload lands. When the *archive* is the convicted party, the relay instead requests a dump from a healthy canonical peer (`desyncDumpRequest`), so the incident record includes a reference state either way. Analysis is `analyze_desync.mjs`: it resimulates the truth from baseline + log, deep-diffs every dumped checkpoint (naming entity, component, and field — including divergence hiding in *unhashed* state, which hash comparison alone never sees), then replays the client's last matching state in lockstep with the truth to pin the exact infection tick; a replay that *doesn't* diverge is itself diagnostic (input-application/timing bug, not a computation bug — the rollback log has the rest). `forge_desync.mjs` forges a real conviction against a live server (publish inputs, rewind through them) to exercise the whole pipeline; verified end-to-end: forged incident recorded, analyzer named the forged ship's `MovementState` (the discarded accelerate input) at the first diverged checkpoint and correctly classified it as a timing divergence. Retention: last 50 incidents, `desyncs/` gitignored.

**First real catch, same day — finding (10), the input-retiming class closed for good.** A solo Firefox session (first non-V8 engine ever run) desynced mid-flight; the black box recorded it, and the analysis was pure deduction from the dump: the rollback log showed *zero* rollbacks (straight-line sim, so timing or math, not netcode churn), `ShipExplodingComponent` differed by exactly one tick's worth of ms (a timing offset, not an ulp leak), and a brute-force replay search found that shifting **one** control record two ticks earlier reproduced the client's checkpoint bit-for-bit across all 189 entities. Verdict: the record arrived ~2 ticks behind the relay clock (a Firefox scheduling hiccup ate the 4-tick pacing lead), the relay retimed it for the room but not the sender — the same asymmetry as findings (4) and (9), now caught in steady state where no clock-seeding patch can prevent it. The structural fix, long deferred, is in: **the relay clamp echo**. Input records carry a sender-assigned `seq`; when the relay clamps a record's tick it echoes the retimed record to the sender, who looks up its local application by `seq`, removes it, re-adds it at the room's tick, and rolls back across the gap — sender and room now apply every record at the same tick *by construction*, regardless of why it was late. Two more fixes from the same incident's timeline: the relay now *holds* checkpoint comparisons until the archive's reference hash exists (comparing early counted a lone peer as self-agreement and reset its mismatch streak — conviction took 737 ticks; now ~145), and clients pin 16 checkpoints instead of 8 (this dump's window missed the divergence origin). The analyzer also gained the origin search as an automatic pass: when the earliest dumped checkpoint already differs, it hunts for a single-record shift that explains the whole window, and on this incident it prints the verdict unaided: "the record logged at tick 283 was applied by the client at tick 281."

**Second real catch — finding (11), the cold-cache class in its second costume: purchased outfits never staged.** A two-tab session desynced ~11s after the second tab joined; the incident record told the whole story without a repro. The clamp echo visibly worked (`retimed` in the uploaded rollback log), checkpoint 18600 matched, and from 18660 exactly *one* component differed for 400 ticks: the new ship's `WeaponsComponent` had six entries on the sender and five everywhere else — the extra being `kinetic things:350`, the weapon granted by a *purchased* outfit in the insertion record's `OutfitsStateComponent`. Root cause chain: `loadShipGameData` staged the ship *class's stock loadout* (`ship.outfits` from game data), not the entity's actual outfits, so the purchased weapon's data never staged on replaying worlds; `WeaponsSystem` gates each weapon on `weaponEntries.getCached(id)` — and `getCached` starts a *background load* on miss — so the weapon's hashed local-state entry materialized at a load-timing-dependent tick, different on every world (`weaponsLocalState` is a DefaultMap that creates entries on access); secondary cycling later read the same cold caches and picked different secondaries per world (`ActiveSecondaryWeapon` diverged), going macroscopic when firing began. Two fixes: `loadEntityGameData` now walks the entity's `OutfitsStateComponent` (weapons, their submunition/bay closures, and the outfit data itself — ammo checks read `Outfit.getCached` too) in addition to stock; and `WeaponsSystem` touches the weapon's local state *before* the cache guard, so hashed state creation is a function of synced `WeaponsState` alone, never of this world's cache warmth. The staging contract now has a direct unit test (a non-stock weapon outfit must be synchronously fireable on a world that staged the entity), and a live node client flying the incident's exact loadout against the archive runs clean. The general lesson joins the determinism rules: **`getCached` in a sim system is only sound if staging provably warmed the id** — entry-creation or behavior gated on cache hits is per-world state masquerading as shared state.

**Third real catch — finding (12), from Chrome Android: flaky links drop insertion records, and failed resyncs strand a fork.** Seventeen convictions of one phone in 23 seconds, and the black box explained every layer. The visible diff (missing/extra asteroids, a diverged `Random` stream, id counter 92 vs 206, `nextRespawn` never scheduled) was ALL downstream of one missing entity: a **ship** whose relayed `addEntity` record the phone never applied — no ship, so none of the asteroid mining that ship did ever happened there. Mechanism: `integrateStaged` staged insertion records with a bare `void load().then(push)`, so one failed mobile fetch silently discarded the record forever (no `lateRecord`, no rollback in the phone's log — the tell). Then the recovery *made it worse*: each conviction's resync timed out (5s join timeout vs a megabyte baseline on a phone link), left the world at restored genesis, and the peer played on — stamping inputs at the room clock from a tick-2000 fork (`retimed {from: 6253}` at `atTick: 2142` in the dump — the smoking gun) and publishing fork hashes that earned conviction every third checkpoint. Three resyncs, zero successful joins. Fixes: staging retries with backoff and, as a last resort, triggers a resync instead of dropping the record; resync itself now retries the whole reconstruction (bounded) with a 20s join window while the sim stays paused — a frozen "reconnecting" client instead of a forked one reporting garbage; join requests space out to 3s so repeated megabyte catch-up replies don't drown the slow link that needed them; and the recorder rate-limits to one incident per room per 30s (the repeats are the same stuck divergence). Also inventoried, not yet fixed: the new asteroid code has four rule-(11) `getCached` sites (respawn type pick, breakup fragments, hurtbox radius from the sprite sheet, scoop outfits) that are safe only because `spawnAsteroids`/staging warm those ids — but `loadAsteroidGameData` swallows load failures with a warn, so a failed fetch there would silently change spawn behavior and even hitbox geometry. Watch item: replace catch-and-warn with retry, and treat "sim data failed to load" as resync-worthy, not warn-worthy. (Fixed same day: `loadWithRetries`, asteroid data throws when unloadable, `getCached` carries the determinism warning in its jsdoc.)

**Fourth session of catches — finding (13), an internet two-player session: the archive itself convicted, and the first fork to (partially) survive analysis.** The room's history: the remote (Safari — a third engine, and notably Chrome↔Safari agreed bit-for-bit all session, so the deterministic Math holds on JavaScriptCore too) convicted twice early and healed; then at tick 57540 the *archive* was outvoted by both browsers — the long-feared poisoned-baseline cascade followed exactly as predicted: the next peer to resync rebuilt from the archive's diverged baseline, flipped sides, and the room re-converged on the archive's timeline while the remaining healthy peer got convicted until its own resync pulled it in too. Self-healing, but onto a forked history. The fork's first mismatched checkpoint (57420) lands 50 ticks after a 25-outfit plugin-heavy purchased-ship insertion; every dumped checkpoint postdates the origin (the archive-outvoted dump *request* took ~28s to answer over the internet link, and the evidence window slid past — retention doubled to 32 checkpoints in response). What analysis DID prove: an offline replay of the recorded log picked a *different secondary weapon* than every live world (`missile things:356` vs `358` — 13 swarm missiles fired on one timeline and not the other, whose ionization then rescaled the victim's `MovementPhysics` by exactly 0.6 and looked deceptively like a derivation bug), because secondary cycling filtered weapons through `Weapon.getCached(id)?.fireGroup` at input-application time — a rule-(11) read in the *input path itself*. Fixed: `fireGroup` now rides inside the synced `WeaponsStateComponent` (derived all-or-nothing with the weapon data present), and cycling/primary-fire read only that state — weapon selection is now a pure function of hashed, synced state. Two open residuals, both about *forensic fidelity* rather than gameplay: (a) the archive-vs-browsers origin at 57420 is unexplained — next such incident will have the doubled window; (b) the analyzer's offline replays parse game data via the test fixture (`getIntegrationGameData`, which suppresses resource-not-found and parses in-process) while live worlds use the server's worker parse — for plugin-heavy content these can genuinely differ, which pollutes replay-based conclusions; the analyzer should consume the exact data the live server serves. **(b) fixed same day**: `SimulationGameData` takes a base URL, and all three analysis tools (`analyze_desync.mjs`, `node_client.mjs`, `forge_desync.mjs`) now fetch from the running server — the same parse the live worlds consumed. Each incident additionally records a `gameDataFingerprint` (sha over the id catalog) and the analyzer compares before replaying: a mismatch prints a loud banner instead of quietly reaching wrong conclusions. Verified end to end, including the mismatch banner on a tampered incident.

**Finding (14) — the archive convicts the innocent (a lagging-client session, 2026-07-16).** Six recorded convictions of one lagging Firefox client, ~30s apart. Stitching a dump with the *next* incident's log (necessary — see the recorder fixes below) proved the convicted client **bit-identical to the clean log replay at nine consecutive checkpoints including the convicted one**: the *live archive* had diverged from its own log's truth, and with a solo peer the server-preferred tie-break convicts whoever disagrees with it. Stranger: the archive's own next baseline was *clean* — its divergence decays, pointing at transiently-wrong self-correcting state (e.g. derived/control state that the next absolute input overwrites) rather than forked spawns. This is finding (13)'s residual, still unexplained — a 150s synthetic lagging-client reproduction (`laggy_client.mjs`: stalls, catch-up bursts, retime storms, NPC combat) failed to provoke it. What changed so the next natural occurrence closes the case: **the archive now retains per-entity hashes at its recent checkpoints and the recorder writes the convicted tick's set into `desync.json`** (`archiveEntityHashes`); the analyzer gained a *replay-verdict pass* that hashes the clean replay at the convicted checkpoint, states which reporter it matches (exonerating the innocent automatically), and diffs the archive's recorded per-entity hashes against the replay — naming the exact entities the live archive got wrong, with zero manual work. Recorder fixes from the same investigation: client dumps are now keyed by their conviction tick (`client_<peer>_tick<N>.json`) — repeat dumps within the incident cooldown used to *overwrite* each other, leaving each directory holding a dump that postdated its own log (self-inconsistent evidence; the analyzer also now skips dump checkpoints beyond the incident log's coverage instead of replaying them into artifact diffs).

**Finding (15) — the first fully-instrumented multiplayer session (four players, 2026-07-21): triage in one pass.** Seven incidents, and the verdict pass sorted them unaided: one genuinely-guilty client conviction that self-healed exactly as designed; one client convicted for the **slow-staging class** — a heavy plugin carrier's insertion record staged slower than the 2s rollback horizon on a friend's connection, so for ~40 ticks that peer's world had no carrier while everyone else's NPCs shot at it (`lateRecord` in its rollback log, `TargetComponent: carrier` vs `undefined` in the diff) — late-staged records now trigger an immediate cooldown-gated resync on top of the apply-asap fallback, rather than waiting seconds for conviction; and five incidents where `archiveEntityHashes` shows the **live archive differing from its own log's clean replay** — finding (14)'s phenomenon, now with named entities: freshly-spawned NPC *pairs* (`npc:185/186`, `npc:3919/3920` — fleet lead + wingman from the new sÿst-dude population system) and just-inserted player ships. Still not root-caused: the spawn plugin's genesis staging contract *reads* correctly, and the divergence remains transient (the archive's baselines stay clean). The closing instrument is now in place: **each incident records the archive's full live wire state at conviction (`archive_state.json`), and the analyzer diffs it against the clean replay at the same tick** — the next occurrence names the diverging components and fields, not just entities. Meta-observation from the session: with echo, staging retries, resync retries, and the frozen-frame fix all landed, every one of the seven incidents self-healed without player-visible breakage — the remaining work is about the archive's honesty as a witness, not about gameplay.

**Recovery made cheap (a53027b7).** The remaining player-visible cost of any desync was the 1–2s rebuild hiccup: reconstruction replayed the log tail over a periodic baseline up to 30s stale — ~1800 ticks of a heavy world resimulated in a blocking loop, capped with a burst of replayed events. Three structural fixes: join requests can ask for a **fresh baseline** (the relay serves the archive's live state, captured on demand and memoized per tick), shrinking the tail to the transit window — and *all* joins default to fresh, so hyperjump arrivals stop paying the stale-tail cost behind the jump flash too; reconstruction fast-forward **yields every 120 ticks** (the worker keeps servicing room traffic mid-rebuild, re-targeting the clock after each pass); and **events emitted during reconstruction are dropped** — they describe history the display already showed, and replaying 30 seconds of explosions in one frame was both the hiccup's tail and a correctness wart. Live-verified: a forged conviction at tick 360 resynced from a baseline captured at tick 479 with zero records to replay. Desyncs will never be exactly zero (new content, new plugins, flaky links); recovery being ~200ms is the resilient-by-design answer.

**Trust model (netcode-security wave, protocol 5).** The rooms were an honour system: the relay stamped a record's sender but forwarded its payload verbatim, the server honoured client-chosen destinations, clients accepted protocol control messages from any source, and nothing was schema-validated — one malformed envelope exited the server process, one forged `removePeer` erased another player's ship for the whole room, permanently. The model is now stated once, in `packages/nova/src/communication/rollback_protocol.ts` ("Trust model"), and every enforcement point cites it by item: the relay stamps identity (1); every boundary validates shape and drops what fails (2); the relay hears room members only and the server never relays client-to-client (3); clients accept rollback messages from the server only (4); and entity-level inputs are authorised deterministically when applied — a peer may remove or replace only what it owns (its ship, the escorts, mission ships and NPCs it inserted), and only the server may `removePeer` (5). Ownership is `ControlledBy.peerId` / `MultiplayerData.owner`, both in synced state, so the drop happens identically on every peer. The content of a peer's *own* inputs is deliberately not policed.

## Decisions

1. **Browser support:** all clients assumed to run latest Google Chrome. ~~No deterministic math layer needed initially; periodic ship state broadcasts (position/velocity/rotation) are the drift backstop.~~ **Superseded by code** (see finding "RESOLVED — the archive-vs-browsers class was cross-engine trig" under Phase 3 item 4): node and Chrome disagree at the ulp level on `Math.sin/cos/atan2/...`, so `makeSystem` installs `nova_ecs/deterministic_math.ts` onto the global `Math` in every simulating context. There are no periodic ship-state broadcasts in the input-driven model; drift is caught by the 60-tick checkpoint hashes and healed by resync (item 4), not papered over by state pushes.
2. **Tick rate:** target 60 Hz; 30 Hz is the acceptable fallback if the Phase 2 benchmark demands it.
3. **Players per system:** ≤ 8–10 per room.
4. **Fallback:** server-authoritative with client-side prediction is acceptable only if it avoids input-round-trip floatiness — the local ship must be predicted locally, never "send keypress, wait for server to say what happened" (a local preview of the attempted action is fine). Phases 0–1 are prerequisite work for that design too, so nothing is wasted up to the Phase 2 checkpoint.
